# AdGuard VPN CLI на Keenetic: несколько профилей и штатная маршрутизация

Практический технический отчёт об интеграции нескольких экземпляров AdGuard VPN CLI с SOCKS-подключениями и DNS-маршрутами KeeneticOS.

**Начать с практики: [команды Web CLI, установка сценариев, проверки и откат](PRACTICAL.md).**

В репозитории есть `service.sh`, `worker.sh`, `health.sh` и шаблон `profiles.example.sh`. Ниже объясняется архитектура; пошаговые действия вынесены в практикум.

**Статус:** экспериментальная архитектура, проверенная на двух устройствах. Это не официальный продукт AdGuard или Keenetic и не универсальный установщик. Полная установка из материалов этого репозитория на чистом устройстве пока не проверена. Не применяйте примеры к рабочей сети без резервной копии и локального доступа для восстановления.

Материал посвящён управлению сетевыми профилями, диагностике и воспроизводимости.

## Задача

Нужно было одновременно поддерживать несколько независимых VPN-профилей, направлять разные группы тестовых ресурсов через разные подключения и управлять маршрутизацией из штатного интерфейса роутера. При этом CLI не должен самостоятельно менять системные DNS-серверы или общий маршрут устройства.

Идея не в разработке нового сетевого протокола. Основная работа состояла в согласовании ответственности двух систем: CLI поддерживает транспорт, KeeneticOS выбирает, какой трафик через него отправлять.

## Архитектура

```text
Клиент локальной сети
        |
        v
DNS роутера -> доменная группа -> штатный DNS-маршрут KeeneticOS
                                      |
                                      v
                            штатное SOCKS-подключение
                                      |
                  +-------------------+-------------------+
                  |                   |                   |
          127.0.0.1:1080       127.0.0.1:1081       127.0.0.1:1082
            профиль A           профиль B           профиль C
                  |                   |                   |
                  v                   v                   v
            VPN-транспорт       VPN-транспорт       VPN-транспорт
```

Адрес `127.0.0.1` обозначает loopback самого роутера. Порты в схеме являются примерами.

Доменное правило не означает, что каждый пакет содержит имя сайта. DNS-маршрутизация зависит от разрешения имён и полученных адресов. Альтернативный DNS клиента, общие адреса CDN, уже открытые соединения и IPv6 требуют отдельных проверок.

SOCKS слушает только loopback. Публиковать его в локальную сеть или интернет для такой интеграции не требуется.

## Проверенный стенд

| Параметр | Наблюдение |
| --- | --- |
| Семейства устройств | Keenetic Viva и Hopper |
| Архитектуры | MIPS и ARM64 соответственно |
| CLI | AdGuard VPN CLI 1.7.12 |
| ОС второго стенда | KeeneticOS 5.1.5 |
| Одновременные профили | Три отдельных процесса |

| Управление маршрутами | Штатные прокси-подключения и DNS-маршруты |

На втором стенде использовалась минимальная среда с официальными ARM64-компонентами Entware и BusyBox, а не полностью установленный пакетный набор Entware. Этот способ развёртывания не предлагается как универсальный. Первую установку среды следует выполнять по актуальной документации для своей модели.

## Подготовка

1. Сохранить конфигурацию роутера и проверить доступность способа восстановления. Конфигурация может содержать секреты: это приватный файл, не приложение к статье.
2. Проверить архитектуру процессора, версию ОС, свободное место и память. Прошивки и бинарные файлы от другой аппаратной версии использовать нельзя.
3. Установить необходимые штатные компоненты: OPKG и клиент прокси. Обновление компонентов может вызвать перезагрузку.
4. Подготовить совместимую среду исполнения и актуальные доверенные CA-сертификаты. Не отключать проверку TLS для исправления ошибок подключения.
5. Получить CLI из официального источника, сверить версию и проверить подпись по доверенному ключу. Проверка только хеша из того же недоверенного источника не подтверждает происхождение файла.
6. Проверить условия подписки и допустимое количество одновременных подключений.

На стенде подпись бинарного файла проверялась; использованная библиотека проверки не выполняла проверку отзыва ключа. Это ограничение метода, а не полноценное доказательство всей цепочки доверия.

## Изоляция профилей

Для каждого экземпляра задаётся отдельный каталог через `AGVPN_CLI_DATA_PATH`. Каталоги должны быть доступны только владельцу процесса. Их содержимое может включать данные авторизации.

Иллюстрация окружения одного профиля, не готовая команда установки:

```sh
export AGVPN_CLI_DATA_PATH=/opt/adguardvpn_cli/profiles/profile-a
export SSL_CERT_FILE=/opt/adguardvpn_cli/ca-certificates.crt
```

Для второго и третьего профилей используются другие каталоги и порты. Не следует переносить полный каталог работающего процесса вместе с сокетами, PID-файлами и журналами. Воспроизводимый порядок отдельной инициализации и авторизации профилей нужно сверять с используемой версией CLI.

Перед подключением и повторно после него необходимо проверить `config show`:

| Параметр | Целевое состояние |
| --- | --- |
| Mode | socks |
| SOCKS host | 127.0.0.1 |
| SOCKS port | Уникален для каждого профиля |
| Tunnel routing mode | none |
| Change system DNS | off |

На стенде первая инициализация соединения изменила ранее заданные параметры маршрутизации и DNS. После её завершения параметры пришлось проверить и восстановить. Это наблюдение для конкретной версии; не стоит считать, что настройки, выставленные до первого подключения, обязательно сохранятся без изменений.

Один процесс запускается с `connect --no-fork -l <LOCATION>`, где `<LOCATION>` выбирается пользователем из актуального списка CLI. Такой запуск удобен для внешнего supervisor: он отслеживает конкретный дочерний процесс.

## Интеграция с интерфейсом Keenetic

Сначала создаётся прокси-подключение в разделе «Другие подключения»:

- протокол SOCKS5;
- сервер loopback и порт нужного профиля;
- понятное название профиля;
- подключение не назначается общим выходом в интернет.

Затем создаётся доменная группа с собственным тестовым ресурсом и DNS-маршрут на это подключение. Начинать стоит с одной группы и одного профиля; добавлять остальные только после успешного клиентского теста.

Пример CLI ниже показывает форму команд. Он намеренно содержит заполнители и **не предназначен для исполнения без адаптации**:

```text
interface <FREE_PROXY_ID>
interface <FREE_PROXY_ID> description "Profile A"
interface <FREE_PROXY_ID> proxy protocol socks5
interface <FREE_PROXY_ID> proxy upstream 127.0.0.1 <FREE_LOCAL_PORT>
interface <FREE_PROXY_ID> down

object-group fqdn <FREE_GROUP_ID>
object-group fqdn <FREE_GROUP_ID> description "Test resources A"
object-group fqdn <FREE_GROUP_ID> include <YOUR_TEST_DOMAIN>

dns-proxy route object-group <FREE_GROUP_ID> <FREE_PROXY_ID>
```

Идентификаторы необходимо выбирать после проверки существующей конфигурации. Пример не описывает все свойства интерфейса и не заменяет документацию вашей версии KeeneticOS. Через веб-интерфейс проще избежать случайного использования занятого идентификатора.

На стенде команда изменения свойства ещё не существующего Proxy-интерфейса завершилась ошибкой. Сначала потребовалось явно создать объект, затем задавать его свойства. Аналогичный порядок использован для доменных групп.

### Важная особенность смены маршрута

Повторное добавление той же доменной группы с другим Proxy-интерфейсом создало второе правило, а не заменило первое. Возникли конкурирующие привязки.

После изменения следует заново прочитать фактическую конфигурацию, например `show sc dns-proxy route`, сопоставить группу, интерфейс и состояние каждого правила. Лишнее правило отключать по его реально прочитанному идентификатору. Не копировать индексы из чужого отчёта.

Один из промежуточных ответов веб-консоли относился к предыдущему запросу. Из-за этого первоначальная интерпретация смены маршрута была неверной. Ответ на отправку команды и прочитанное после её завершения состояние нужно различать.

### Что делает переключатель

Переключатель штатного прокси-подключения управляет этим подключением в KeeneticOS. Он **не является кнопкой завершения фонового процесса AdGuard VPN CLI**. Процесс может продолжать поддерживать туннель.

Поведение трафика при выключенном прокси нужно проверить отдельно. В этой работе не доказано, что он обязательно блокируется, а не получает другой маршрут. Решение не следует использовать как гарантированный kill switch.

## Автозапуск и контроль состояния

На стенде использовался небольшой supervisor для каждого профиля:

1. Проверить наличие бинарного файла и конфигурации.
2. Проверить, что локальный порт свободен.
3. Запустить CLI как дочерний процесс.
4. Выполнить HTTP-запрос через SOCKS с передачей имени целевого узла прокси-серверу.
5. При нескольких последовательных неудачах остановить только свой дочерний процесс и повторить подключение после паузы.
6. Ограничивать размер диагностических журналов.

Для остановки проверялась принадлежность PID ожидаемому исполняемому файлу. Широкие команды вроде остановки всех процессов с похожим именем не нужны.

Автозапуск был подключён к OPKG через initrc. Нельзя безусловно заменять существующий initrc: он может запускать другие службы. Сначала требуется изучить его содержимое и сохранить оригинал.

Ограничения испытанного supervisor:

- при гибели самого supervisor отдельного watchdog для его восстановления нет;
- остановка и повторный запуск исправлены и проверены на Hopper; при аварийной гибели управляющей команды её отдельный lock-каталог может потребовать ручной диагностики;
- тест HTTP не покрывает все прикладные протоколы;
- усечение журнала ограничивает его размер, но не является полноценной ротацией;
- долговременная устойчивость и поведение при исчерпании памяти систематически не измерены.

Исправленный вариант сценариев прошёл локальные тесты и цикл stop/start на Hopper. На Viva это исправление пока не установлено. Версия сценариев из репозитория ещё не прошла полную установку на чистом устройстве. Это примеры для контролируемого развёртывания, не готовый универсальный production-пакет.

## Как проверять результат

Нужно разделять четыре разных утверждения:

1. **Процесс запущен.** Проверка PID подтверждает только существование процесса.
2. **SOCKS передаёт данные.** Успешный тест через локальный порт подтверждает путь через этот экземпляр.
3. **Выход соответствует профилю.** Внешний тестовый ресурс показывает наблюдаемый адрес/регион. Геолокационные базы могут расходиться; это не физическая аттестация сервера.
4. **Клиентское приложение использует нужный маршрут.** Требуются отдельный тест с клиента, свежая сессия и проверка возможных альтернативных путей.

На стенде все три канала прошли тест передачи данных после перезагрузки без ручного запуска. Отдельно проверялся выход одного профиля; пользователь подтвердил работу нескольких приложений.

Ни успех приложения, ни IP-тест с самого роутера по отдельности не доказывают отсутствие утечек для всего клиентского трафика.

На iPhone с iOS 27 обнаружен отдельный фактор: при включённых Wi-Fi и сотовых данных клиентский результат отличался от режима только Wi-Fi. Отключение Connectivity Assist для тестовой Wi-Fi-сети устранило проблему. Не установлено, уходил ли альтернативным путём DNS или прикладной трафик. [Описание параметра у Apple](https://support.apple.com/en-gb/guide/iphone/iphw5gjwl8k2/ios).

## Восстановление

До начала работы сохранить исходную конфигурацию и список создаваемых объектов. При проблемах сначала отключать только добавленные DNS-правила и прокси-подключения, затем останавливать соответствующие процессы. Не очищать всю таблицу маршрутов и не удалять чужие правила.

Откат изменений initrc должен сохранять работу существующих служб. Резервная копия настроек Keenetic и резервная копия файлов среды OPKG являются разными частями восстановления; одна не обязательно содержит другую.
